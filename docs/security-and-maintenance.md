# 운영 제한과 개선 우선순위

## 적용한 보호 장치

- 기본 서버 주소는 `127.0.0.1`. LAN 공개는 `HOST=0.0.0.0`으로 명시한다. 기존 `.env`의 HOST 설정은 유지되므로 확인한다.
- AI 요청은 모든 AI 경로를 합산해 IP별 시간당 12회, 서버 전체 24시간당 100회로 제한한다. `.env`의 `AI_REQUESTS_PER_HOUR`, `AI_TOTAL_REQUESTS_PER_DAY`로 조정한다. 실제 토큰 비용 한도는 아니며 실패한 요청도 집계한다.
- YouTube GET 경로는 IP별 시간당 20회, 서버 전체 24시간당 60회로 합산 제한한다. `YOUTUBE_REQUESTS_PER_HOUR`, `YOUTUBE_TOTAL_REQUESTS_PER_DAY`로 조정하며 캐시 적중·실패도 수신 요청으로 집계한다. 인코딩·세미콜론 등 모호한 경로 표기는 라우팅 전에 400으로 거부한다.
- 모든 POST 요청에 IP별 분당 60회 제한을 추가한다. 조회는 IP와 대상 경로별 30분당 1회다. 좋아요와 리뷰는 각각 IP별 분당 10회이며 모든 대상을 합산한다. 좋아요 취소와 리뷰 수정도 이 예산 내에서 즉시 가능하다. UUID를 바꾸어도 제한되며 같은 공유기 사용자도 제한을 공유한다.
- 초과 요청은 HTTP 429와 `Retry-After` 초 단위를 반환한다. 전달된 `X-Forwarded-For`를 신뢰하지 않는다.
- 카운터는 메모리에만 보관하며 만료 항목을 제거하고 크기를 제한한다. 재시작하면 초기화된다. 여러 서버 배포에는 Redis 등 공유 제한 저장소와 인증이 필요하다. 역방향 프록시 뒤에서는 프록시 IP 기준으로 합산된다.
- 깨진 `CookingHelper/` gitlink를 제거했다. 기존 중첩 체크아웃은 로컬 파일을 보존하고 ignore 처리했다.
- 앱 저장 JSON이 손상되면 `.corrupt` 키에 원본을 보관하고 레거시 데이터 또는 기본값으로 복구한다.
- 오류 화면, 비 JSON API 응답 처리, GitHub Actions 타입 검사·빌드·테스트를 추가했다.

## 구현한 기능과 사용 방법

### 커뮤니티와 신고 관리

새 글·댓글 등록 응답에만 서버 발급 작성 권한을 반환하고, 기기 저장소에 보관한다. 서버에는 SHA-256 해시만 저장한다. 작성 기기에서는 글·댓글의 수정·삭제 버튼이 보이고, 삭제 시 확인을 거친다. 응답 객체를 변경하지 않고 권한을 복사하므로 지연된 상태 갱신도 안전하다. 기기 저장 실패 시 등록 성공 상태를 유지하며 화면에서 권한 저장만 재시도할 수 있다. 재시도 전 화면을 닫으면 미저장 권한이 사라질 수 있으므로 화면의 안내를 따른다. 공개 조회에는 토큰과 해시가 포함되지 않는다. 기존 글은 작성 권한이 없으므로 관리자를 통해 처리한다. 기기 초기화 시 작성 권한을 복구하는 계정 기능은 아직 없다.

글·댓글·레시피 신고는 공통 신고 저장소에 들어간다. `ADMIN_KEY`를 서버 `.env`에 충분히 긴 임의 문자열로 설정하고, 내 주방 → 신고 관리에서 입력한다. 비어 있으면 관리자 접근이 비활성화된다. 키는 앱에 저장하지 않는다. 미처리 신고를 조회해 검토 완료하거나 대상 글·댓글을 삭제하고 레시피를 숨길 수 있다. 기존 레시피 신고도 최초 조회 시 가져오며 처리 결과는 유지된다. 외부 배포 시 HTTPS를 사용한다.

### 타이머

조리 단계 화면에서 화면 꺼짐 방지를 활성화한다. 네이티브 앱에서는 시작 시 알림 권한을 확인하고 로컬 알림을 예약한다. 일시정지·단계 이동·조리 종료·화면 닫기는 해당 알림을 취소한다. 권한 거부나 예약 실패 시 안내와 화면 타이머를 유지한다. 웹은 화면 내 타이머를 사용한다.

기기 알림 설정과 배터리 정책에 따라 지연될 수 있다. Android 정확한 알람 권한을 선언했으며 기기 설정에 따라 허용이 필요하다. 실제 Android/iOS 기기의 알림음·잠금 화면·화면 유지·권한 거부 동작은 출시 전 확인해야 한다. 앱 강제 종료 후 조리 화면 복원은 지원하지 않는다. API 기준: [Expo Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/).

### 백업

내 주방 → 데이터 백업에서 JSON 파일로 내보내고 가져온다. 레시피·설정·재고·장보기·요리 기록·닉네임을 포함한다. 버전과 UTF-8 기준 5MiB 용량 제한 및 필드 검증을 통과한 파일만 교체 확인 화면에 표시한다. 내보내기와 가져오기는 같은 바이트 기준을 쓴다. 로컬 저장 복구는 필드별로 수행하여 잘못된 설정만 기본값으로 돌리고 유효한 레시피·기록은 유지하며, 원본은 `.corrupt` 키에 보관한다. 가져오면 현재 데이터를 교체하므로 먼저 현재 백업을 내보낸다. 커뮤니티 작성 권한과 viewer ID는 백업 대상에서 제외한다.

### DB 이전

레시피·카탈로그·조회·리뷰·채널, 커뮤니티 글·댓글·좋아요, 신고는 임베디드 H2에 저장한다. 각 저장 디렉터리의 `store.mv.db` 파일을 사용한다. 사진 바이너리는 기존 파일 경로를 유지한다. 최초 접근 시 유효한 레거시 JSON을 하나의 트랜잭션으로 이전한다. 오류가 나면 롤백하고, 완료 표시는 성공한 트랜잭션에만 남긴다. 기존 JSON은 지우지 않으며, 재시작해도 다시 가져오지 않는다. 변경 즉시 기록하도록 `WRITE_DELAY=0`을 사용한다.

백업할 때는 서버를 종료한 뒤 각 저장 디렉터리 전체를 복사한다. 운영 후 예전 JSON으로 돌아가면 DB에 기록한 수정·삭제가 반영되지 않으므로 원본 JSON은 초기 복구용으로만 사용한다. 문서 테이블과 함께 카탈로그 색인·조회 이벤트 집계를 둔다. 첫 접근 시 기존 H2 문서에서 색인을 한 번 생성하고, 이후 원본 문서와 같은 트랜잭션에서 갱신한다. 필터·정렬·중복 제거·페이지 처리·기간별 랭킹·영상 ID 조회를 SQL로 수행하여 목록 요청마다 모든 원본 JSON을 읽고 파싱하는 경로를 제거했다. 포함 문자열 검색은 SQL에서 수행하므로 대규모 검색에는 추후 전문 검색 색인이 필요하다. DB 기준: [H2 기능 문서](https://h2database.com/html/features.html).

같은 영상과 같은 메모로 동시에 들어오는 분석은 단일 JVM 내 진행 중 요청을 공유한다. 실패하면 공유 상태를 제거하여 재시도할 수 있다. 분석이 끝난 기본 영상 요청은 저장 결과를 재사용한다. 여러 서버 인스턴스로 확장하면 분산 잠금 또는 작업 큐가 추가로 필요하다.

### 유지보수와 자산

주방 데이터·추천 결과·가이드·화면 상태와 동작의 Context 구독을 분리하고 안정적인 액션 참조를 사용한다. 레시피 후기·신고·완료 UI와 타이머 훅, 작성 권한·DB·관리자 API를 별도 파일로 나눴다. `npm run lint`, `npm run format`, `npm run format:check`를 제공하며 CI에서도 검사한다.

앱 아이콘·Android adaptive icon·스플래시를 설정했다. `assets/app/icon.svg` 수정 후 `npm run assets:app`으로 PNG를 다시 생성한다. 변경된 네이티브 설정은 앱 재빌드가 필요하다. 전환 전 코드는 `archive/legacy/`로 옮겨 실행·검사 대상과 구분했다. PPT는 사용자 요청대로 이동·수정하지 않았다.

소비기한 정렬·임박 표시·재료 우선 추천은 기존 동작을 유지했다.

## 검증

`npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test`. `npm test`와 `npm run test:spring`은 각각 `pretest`와 `pretest:spring`에서 웹 내보내기 후 Gradle `build`를 실행한다. 깨끗한 clone에도 최신 UI와 서버 jar를 준비하며, 빌드 실패 시 테스트를 실행하지 않는다. CI도 같은 흐름을 사용한다. `node --test`를 직접 실행하면 이 빌드 단계가 생략되므로 해당 명령은 최신 jar를 준비한 경우에만 사용한다.

통합 테스트는 실제 OpenAI 대신 로컬 fixture를 사용한다. UUID 변경 및 위조 전달 헤더로 제한을 우회할 수 없는지 검증한다.
